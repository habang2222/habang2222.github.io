# 1. 소개

문제 : 파이썬의 공격적 언어 개선, 불안정한 바이트코드 규칙으로 파이썬 디컴파일 도구 유지가 어렵다.

목표 : 최소한의 유지 관리 노력으로 바이트코드 규칙의 진화하는 언어 특징과 변경 사항을 수용하는 파이썬 디컴파일러를 만드는 것, 분해된 바이트코드 시퀀스에서 파이썬 소스 코드를 복구

- *바이트코드 : 고급 프로그래밍 언어로 작성된 소스 코드를 소스 코드와 기계어 사이의 중간 표현으로, Python 인터프리터나 JVM 같은 가상 머신이 해석하거나 실행할 수 있는 코드

PYLINGUAL : 데이터 기반 NLP(자연어 처리) 구성 요소를 버전에 구애받지 않는 코어에 삽입하여 표면적인 바이트코드와 컴파일러 변경 사항을 자동으로 흡수하고, 추상 제어 흐름 재구성을 위한 프로그래밍적 구성 요소를 활용해 디컴파일하는 프레임워크

- 프레임워크 : 프로그램을 만들 때 쓰는 기본 틀

기여 : 

- PYLINGUAL을 제시하여 파이썬 3.6~3.12 버전 지원을 제공하여 4가지 데이터셋에서 기존 디컴파일러의 최고 결과보다 완벽한 디컴파일 비율을 평균 45% 향상시킴
- 완벽한 디컴파일로 디컴파일 결과를 검증하는 파이썬 디컴파일러 평가 프레임워크를 제공
- PYLINGUAL을 공개 온라인 서비스로 출시

컴퓨팅 환경이 다양해지고 특정 타깃과 시나리오에 맞춘 공격 벡터의 수요가 커지면서, Python 디컴파일 수요도 증가하고 있습니다
폐쇄형 소스 프로그램 분석에서도 Python 디컴파일 수요가 커진다. 

파이썬 디컴파일러는 패키지된 실행 파일을 풀어 Python compiled file(PYC) 바이너리를 추출하고 바이트코드 시퀀스로 분해하고 최종적으로 소스 코드를 복구합니다.

- *컴프리헨션 : 반복문을 짧게 써서 리스트 딕셔너리 집합 등을 만드는 문법


중첩된 코드 객체 구조를 가지는 파이썬 코드입니다

A는 파이썬 원문 B는 코드가 어떤 구조인지 보여주는 그림

최상위 스크립트는 main코드 객체라고 불립니다

객체들은 바이트코드 명령어 메타데이터 디버깅 메타데이터 등으로 이루어져 있습니다.

메타데이터가 포함하는 것 :

유용한 특성: 파이썬 바이트코드의 구조는 함수의 경계가 명확하게 구분되어 있기 때문에 디컴파일 과정에서 어려운 여러 하위 작업들을 단순화한다.

Python에서 제어 흐름은 크게 네 가지 범주로 나눌 수 있다

점프, 함수 호출, return, 예외 처리

Python에서 점프 대상은 정적으로 결정됩니다. 또 코드 객체의 경계를 넘어갈 수 없습니다 

이게 무슨 말이냐 정적이란 말은 실행하기 전에 이미 구조가 정해져 있다는 말이다

예 ) 

if x > 0:
print("positive")
else:
print("zero or negative")

이 코드를 바이트코드로 바꾸면 

x > 0 검사
거짓이면 else 부분으로 점프
참이면 if 부분 실행
if 끝나면 else를 건너뛰고 다음 코드로 점프

이렇게 보인다

여기서 고정이 무슨 말이냐하면 

거짓이면 몇 번째 명령어로 이동할지
if 끝나면 몇 번째 명령어로 이동할지 

이러한 정보가 바이트코드 안의 숫자 혹은 위치로 저장되어 있다는 뜻입니다

이 말은 실행할 때마다 전혀 다른 함수 안으로 점프하는 상황은 벌어지지 않는다는 뜻이다

하지만 함수 호출은 동적이다

예 ) print(”nogod”)

이 코드는 print 함수를 호출하는 것 처럼 보이지만 실행 전에 

print = my_func

print(”nogod”)

이렇게 되면 원래 함수인 print 가 호출되는 게 아니라 my_func 함수가 실행된다

즉 함수 호출 대상은 실행 중에 결정될 수 있다

한마디로 Python에서 if/while/for 같은 점프 구조는 바이트코드만 봐도 위치를 알 수 있다 하지만 함수 호출은 실제 실행 전까지 정확히 어떤 함수가 호출될지 모를 수 있다

하지만 함수 호출 대상은 실행 시간에 결정됩니다. 이러한 설계는 함수 심볼을 동적으로 다시 할당 할 수 있게 해 줍니다

*심볼: 프로그래밍에서 어떤 값 함수 변수 객체를 가리키는 이름

return은 함수의 실행을 멈추고 값을 반환합니다 하지만 yield문이 있는 경우 함수가 나중에 실행을 다시 이어갈 수도 있습니다

yield문이 있는 경우는 함수가 완전히 끝나는 게 아니라 중간에 멈췄다가 나중에 다시 이어서 실행될 수 있다는 뜻

보통은 return을 만나면 끝나지만

yield가 있으면 그 함수는 제너레이터 함수가 됩니다

def gen():
yield 1
yield 2
yield 3

이 함수는 한 번에 끝까지 실행되지 않고

g = gen()

print(next(g))  # 1
print(next(g))  # 2
print(next(g))  # 3

흐름은

next(g) 호출
→ yield 1에서 멈춤
→ 1을 밖으로 내보냄

다시 next(g) 호출
→ 아까 멈춘 yield 1 다음 줄부터 재개
→ yield 2에서 멈춤
→ 2를 밖으로 내보냄

다시 next(g) 호출
→ yield 2 다음 줄부터 재개
→ yield 3에서 멈춤
→ 3을 밖으로 내보냄

return : 값을 반환하고 함수 종료
yield : 값을 반환하듯 내보내지만 함수 상태를 저장하고 일시 정지
next() : 멈췄던 yield 다음부터 다시 실행

디컴파일러 입장에서는 함수 호출에는 굉장히 많은 심볼들이 사용될 수 있기 때문에 소스 코드를 복원할 때는 각 코드 객체 내부의 제어 흐름 구조만 고려하면 된다는 것이다

점프와 return만 모델링하는 제어 흐름 그래프를 만드는 것은 비교적 쉽다 그리고 앞에서 본 것처럼 Python 디컴파일에서는 함수 호출을 사실상 무시해도 된다

Python의 예외 처리 구조를 모델링하려면 버전에 따라 다른 논리가 필요하다 최근 몇 년 동안 Python의 예외 처리 구조는 상당히 많이 바뀌었기 때문이다

파이썬 바이트코드를 디컴파일할 때 제어 흐름을 어떻게 이해해야 하는가를 설명하는 부분

Python에서 if, while, for 같은 점프 구조는 바이트코드 안에서 비교적 명확하게 정해져 있다 하지만 함수 호출을 실행할 때 실제로 어떤 함수가 불릴지 결정된다

Python 버전이 올라갈 때마다 opcode가 계속 바뀌었다는 뜻

Python 바이트코드의  구조는 디컴파일의 많은 부분을 단순하게 만들어 준다 하지만 Python 언어의 개발 방식은 새로운 문제들을 계속 만들어 냈고 이 때문에 커뮤니티 기반 디컴파일러들이 충분히 성숙하는 것을 방해한다

## 명세 불안정성

Python 디컴파일에서 가장 중요한 어려움은 Python 바이트코드 명세가 불안정하다는 점입니다

*바이트코드 : 사람이 쓴 코드를 컴퓨터가 바로 실행하기 좋게 바꾼 중간 단계 명령어

Python은 처음 공개된 이후 버그 수정 성능 향상을 빠르게 반영해 왔다 하지만 매년 발표되는 minor 버전마다 Python 언어 기능과 바이트코드 표현 방식에 상당한 변화가 생겼다 

Java 바이트코드와 비교를 해보면 Java는 10년 동안 opcode 변화가 거의 없는 반면 Python은 거의 매년 opcode 상당 부분이 바뀌는 것이 일반적입니다

이러한 차이는 Python 개발팀은 성능 향상과 유용한 언어 기능을 위해 언어를 과감하게 바꾸는 방식을 선호하기에 이러한 결과가 나옵니다

opcode 정의가 바뀌는 것뿐만 아니라 각 Python 버전은 코드 생성 방식에도 문서화가 부족한 변화를 만듭니다 이것은 Python 디컴파일러를 유지보수하는 데 필요한 노력을 더 크게 만듭니다

Python 커뮤니티에서는 Faster CPython 프로젝트를 진행했습니다. 그 결과 인터프리터가 제어 흐름을 관리하는 데 쓰는 시간을 줄이기 위해 명령어를 재정렬하는 최적화가 이루어졌습니다 

이 최적화들 중에서 가장 주목할 만한 것은 zero-cost exceptions 입니다

Python 3.11 에서 도입된 이 방식은 예외 처리 메커니즘을 완전히 다시 설계했습니다 기존에는 예외 처리를 위해 block stack을 사용했지만 Python 3.11부터는 exception table을 사용합니다

- *Faster CPython : Python 공식 구현체인 CPython을 더 빠르게 만들기 위한 성능 개선 프로젝트
    - CPython : Python 언어를 C 언어로 구현한 공식 인터프리터
- *zero-cost exceptions : 직역하면 비용이 0인 예외 처리
    - 예 )
    
    try:
    x = 10 / n
    except ZeroDivisionError:
    print("0으로 나눌 수 없음")
    
    이 코드가 정상 실행되면 원래는 Python 인터프리터가 내부적으로 관리했습니다 
    즉 예외가 안 터져도 예외 처리를 위한 관리 비용이 있었던 것이다
    
    ```go
    지금 try 블록 안에 들어왔음
    예외가 나면 어디 except로 가야 함
    finally가 있으면 어디를 실행해야 함
    블록 스택에 정보 저장
    ```
    
    근데 3.11부터는 exception table 이라는 별도의 표를 둔다
    
    ```go
    예전 방식:
    실행하면서 계속 "지금 try 안에 있음" 같은 정보를 들고 다님
    
    Python 3.11 방식:
    평소에는 그냥 실행
    예외가 실제로 터졌을 때만 exception table을 보고 처리 위치를 찾음
    ```
    
- * block stack : 파이썬 인터프리터가 실행 중에 지금 어떤 코드 블록 안에 있는지 기억해 두는 내부 기록장
    - block 구조
    
    ```go
    try:
        ...
    except:
        ...
    
    for ...:
        ...
    
    while ...:
        ...
    
    with ...:
        ...
    ```
    
    - { } 같은 코드 블록이 아니라 예외 처리나 반복문처럼 실행 흐름을 관리해야 하는 구역
    - 필요한 이유는 예전 파이썬은 try -except-finally 같은 구조를 실행할 때 내부적으로 이런 정보를 저장해야 했습니다
        
        현재 try 블록 안에 있음
        예외가 발생하면 어느 except로 가야 함
        finally가 있으면 어디를 실행해야 함
        반복문 break가 나오면 어디로 가야 함
        
        이러한 정보를 쌓아 두는 곳이 block stack 이다
        
    - 예시 )
    
    try:
    x = 10 / n
    except ZeroDivisionError:
    print("0으로 나눔")
    
    - 내부적으로 위 코드를
    
    block stack에 저장:
    
    - try 블록 시작
    - 예외 발생 시 except 위치로 이동
    
    이런 식으로 기록합니다 
    만약 정상 실행되면 block stack에서 try 정보 제거
    
    예외 처리가 되면
    
    ZeroDivisionError 발생
    → block stack 확인
    → 가장 가까운 예외 처리 블록 찾음
    → except ZeroDivisionError 위치로 이동
    
    - 이러한 흐름으로 처리합니다
    - 즉 파이썬 인터프리터가 실행 중에 try for with 같은 제어 블록 정보를 쌓아두고 예외나 break finally 같은 흐름을 처리하기 위해 쓰던 내부 스택
        - 인터프리터는 사람이 쓴 코드를 읽고 한 줄씩 해석해서 실행시켜주는 프로그램
- exception table

특정 파이썬 버전 하나에만 사용하는 디컴파일러를 만드는 것은 그냥 공학적 문제이지만 진짜 어려운 점은 여러 버전에서 사용 가능하게 확장하는 문제입니다 이유는 앞에서 말했듯이 새로운 기능이 너무 많이 도입되고 바이트코드의 명세가 예측 불가능하게 바뀌기 때문입니다

기존 파이썬 디컴파일 프레임워크들은 손으로 작성한 버전별 문법 규칙과 문장 패턴에 의존합니다 그래서 파이썬의 새로운 버전이 나오는 속도를 따라가지 못했습니다

PYLINGUAL은 기존 디컴파일러처럼 버전마다 사람이 직접 규칙을 고치는 방식이 아니라 학습된 AI/NLP 모델을 갈아 끼우는 방식으로 디컴파일러를 만든다는 뜻입니다

최근 PyFET같은 연구는 전처리 과정을 통해 기존 디컴파일러들의 지원 범위를 개선하려 했습니다 하지만 이러한 연구들은 수정된 결과를 신뢰할 수 있는지 확인하기 위한 강력한 출력 검증 방식이 부족했습니다

이러한 전처리 방식들은 파이썬의 공격적인 개발 주기를 지속적으로 지원할 수 있는 디컴파일러를 만드는 데 있어 이 논문의 방법과 서로 도움을 준다

1. PYLINGUAL은 소스 코드와 디스어셈블된 바이트코드에 대해 코드 정규화를 수행합니다. 이는 NLP 모델에 입력되는 데이터의 복잡도를 줄이기 위한 것입니다 (5.1 설명)
2. 정규화된 코드 객체들은 바이트코드 분할 구성 요소로 전달됩니다. 이 단계에서는 문장 단위의 경계를 식별합니다. (5.2 설명)
3. 문장 번역 구성 요소는 바이트코드와 각 문장을 그에 대응하는 파이썬 소스 코드 문장으로 번역합니다. (5.3)
4. 제어 흐름 복원 구성요소는 입력 바이트코드의 제어 흐름을 재현하는데 필요한 들여쓰기를 기계적으로 복원합니다 if, while, for, try 같은 흐름 구조가 소스 코드에서 제대로 보이도록 들여쓰기를 맞추는 단계입니다. (5.4)
5. 코드의 동등성 검증은 명령어 수준의 코드 비교를 수행합니다 이를 통해 디컴파일된 파이썬 소스 코드가 올바른지 검증하는 단계입니다. (5.5)


그림 4는 PYLINGUAL 작업 흐름의 단순화된 예시입니다

PYLINGUAL이 바이트코드를 어떻게 Python 소스 코드로 바꾸는지 보여줍니다  

예 )  if <MASK_1> == False:

이런 식으로 먼저 마스크가 들어간 형태로 번역한 뒤 아래의 mask-value table을 통해 MASK_1, MASK_2, MASK_3 같은 값을 실제 이름이나 값으로 채웁니다

이 도구에는 파이썬 3.11과 3.12 바이너리를 디스어셈블할 수 있도록 지원하는 코드가 추가되었습니다

다음 PYLINGUAL은 PYC 바이트코드의 복잡도를 줄이기 위해 변수 이름이나 상수값 정보들을 일반적인 패턴으로 대체합니다

이 마스크들은 PYC 바이너리의 메타데이터 테이블 인덱스를 바탕으로 만들어집니다. 원래 값은 따로 저장해 두었다가 디컴파일 마지막 단계에서 다시 소스 코드 수준으로 복원합니다.

또한 PYLINGUAL은 바이트코드 명령어의 표현을 개선합니다. 구체적으로 예외 처리 구조를 나타내는 점프 대상에 주석을 붙입니다 이런 입력 전처리 단계 덕분에 PYLINGUAL은 NLP 모델에 들어가는 입력을 표준화할 수 있습니다  그래서 바이트코드 표현 방식이 크게 바뀌더라도 NLP 모델이 처리하는 입력 형태를 어느 정도 일정하게 유지할 수 있습니다

PYC: Python 소스 코드(.py)를 실행하기 위해 Python 인터프리터가 컴파일해 둔 바이트코드 파일

NLP: 자연어 처리 사람이 쓰는 언어를 컴퓨터가 이해하거나 처리하게 만드는 기술

5.2

분할 모듈의 목표는 2가지입니다

1. 번역 모듈을 지원하기 위해 바이트코드를 독립적으로 처리할 수 있는 문장 단위로 나눕니다
2. 제어 흐름 복원을 지원하기 위해 바이트코드 명령어들을 그에 대응하는 소스 코드 문장과 연결합니다
3. 소스 코드에서 사용하는 문법적 개념인 문장을 활용하여 하나의 소스 코드 문장에 직접 대응되는 바이트코드 명령어들

소스 코드에 접근할 수 있는 통제된 환경에서는 바이트코드 문장을 얻을 수 있습니다 

먼저 파이썬의 ast 모듈을 사용해 각 소스 코드 문장이 서로 다른 줄에 오도록 만듭니다 그다음 생성된 PYC 바이너리 안의 줄 번호 정보를 참고하여 바이트코드 명령어를 해당 소스 코드 문장과 연결합니다 

하지만 통제되지 않은 환경에서는 PYC 바이너리 안의 줄 번호 정보가 바이트코드 문장을 식별하는 기준이 되지 않습니다. 이유는 줄 번호 정보는 디버깅 메타데이터라 바이트코드 실행에는 영향을 주지 않고 자유롭게 조작 되거나 생략 가능합니다. 또 하나의 문장이 여러 줄에 걸쳐 있을 수 있습니다 또 반대로 여러 문장이 한 줄에 있을 수도 있기 때문에 디컴파일 과정에서 바이트코드 문장을 확장 가능하게 식별하기 위해 저자들은 각 대상 파이썬 버전마다  BERT 기반 분할 모델을 학습시킵니다

이 분할 모델의 역할은 각 바이트코드 명령어가 다음 중 어디에 해당하는지 예측하는 것 입니다

| 라벨 | 의미 |
| --- | --- |
| `Begin` | 새 문장을 시작함 |
| `Internal` | 현재 문장 내부에 있음 |
| `End` | 현재 문장을 끝냄 |

Statement Translation은 앞 단계에서 문장 단위로 나눠진 바이트코드를 다시 파이썬 소스 코드 문장으로 번역합니다 지금까지는 바이트코드 명령어를 문장 단위로 자르고 바이트코드 문장을 파이썬 소스 코드 문장으로 바꿉니다

논문에서는 이 작업을 NLP에서 많이 쓰는 시퀀스-투-시퀀스(sequence-to-sequence) 번역 문제로 봅니다 그래서 PYLINGUAL은 바이트코드 한 문장을 파이썬 소스 코드 한 문장으로 바꾸기 위해 인코더-디코더(encoder-decoder) Transformer 모델을 학습시킵니다

예)

바이트코드가

LOAD_GLOBAL <MASK_2>
LOAD_METHOD <MASK_3>
LOAD_FAST <MASK_4>
CALL_METHOD
POP_TOP

이런 식으로 있으면 이걸 번역 모델이 

<MASK_2>.<MASK_3>(<MASK_4>)

이러한 파이썬 문장으로 바꿉니다

그다음 마스크 값을 복원하면 

os.mkdir(target_folder)

이런 식이 됩니다

논문은 일반 NLP 토크나이저를 그대로 사용하지 않고 파이썬 전용 토크나이저를 사용합니다 이유는 파이썬 소스 코드와 파이썬 바이트코드는 일반 자연어 문장과 다르기 때문입니다 이런 구조에서 os, ., mkdir 같은 토큰 구조가 중요합니다

그래서 PYLINGUAL은 파이썬 바이트코드 명령어 문서와 파이썬 소스 코드 문법을 바탕으로 커스텀 토크나이저를 만듭니다 이렇게 하면 의미가 여러 토큰으로 쪼개져 흐려지는 문제를 줄이고 번역의 일관성을 높일 수 있습니다

PYLINGUAL은 번역 모델 하나만 사용하지 않습니다 추가로 보정 모델(corrector model) 즉 보정 모델을 사용합니다 이 보정 모델은 번역이 어려운 바이트코드 문장을 고치는 역할을 합니다 논문에서 말하는 어려운 문장 예시는 

list comprehension
큰 boolean expression
복잡한 함수 정의

[x for x in arr if x > 0]

혹은

if a and b and c or d:
...

이런 문장들은 앞부분을 제대로 번역하려면 뒤쪽 구조까지 알아야 할 때가 있습니다 논문은 이런 어려움이 자기회귀 디코더(autoregressive decoder) 의 약점과 관련 있다고 설명합니다 그래서 보정 모델은 원래 바이트코드와 1차 번역 결과를 함께 입력 받아서 전체 번역을 보고 불일치를 수정합니다

---

이러한 과정이 끝나면 파이썬 문장들을 얻을 수 있습니다

하지만 이 상태는 그냥 평범한 문장 목록입니다 무슨 말이냐 하면 들여쓰기가 없거나 흐름이 제대로 안 맞으면 파이썬 코드로 실행할 수 없습니다 그래서 5.4에서는 번역된 문장들을 조립해서 원래 PYC 바이너리의 제어 흐름을 반영하는 완전한 파이썬 프로그램으로 만듭니다 논문은 이 과정을 세 단계로 나눕니다 CDG 구성, 들여쓰기 annotation, 소스 코드 줄 배치 

1. Control Flow Graph(CFG) 를 만듭니다
CFG는 코드의 실행 흐름을 그래프로 표현 한 것입니다 
    
    명령어 A
    ↓
    명령어 B
    ↓
    조건에 따라 C 또는 D
    
    파이썬 바이트코드는 간접 점프가 없고 코드 객체마다 따로 볼 수 있기 때문에 각 코드 객체에 대해 정적인 CFG를 만들 수 있습니다 cfg에서 각 명령어는 노드가 되고 간선은 실행 흐름을 나타냅니다 논문은 간선을 3종류로 설명합니다 다음 명령어로 가는 natural edge 점프 명령어로 이동하는 jump edge 예외 핸들러로 가는 exception edge가 있습니다 
    
2. CFG를 만든 뒤에는 CDG를 만듭니다
    
    cfg가 코드가 어디로 이동하는가를 보여준다면 CDG는 어떤 조건이 어떤 코드의 실행 여부를 결정하는가 를 보여줍니다
    
    예 ) 
    
    if x > 0:
    print("positive")
    
    여기서 print("positive")가 실행되는지는 if x > 0 조건이 결정합니다
    
    그래서 CDG 관점에서는 
    
    if x > 0
    ↓
    print("positive") 실행 여부 결정
    
    이런 관계가 됩니다 논문은 cfg에서 제어 결정이 어떤 basic block 의 실행 여부를 결정하는지 보고 CDG를 만든다고 번역합니다
    
3. 파이썬은 들여쓰기 문법입니다 
    
    if x > 0:
    print("positive")
    
    여기서 print앞의 들여쓰기가 없으면 코드 의미가 깨집니다
    
    PYLINGUAL은 CDG를 이용해서 각 basic block이 얼마나 깊게 중첩되어 있는지 계산하고 그에 맞게 들여쓰기 레벨을 붙입니다 보통은 cdg에서 START 노드와의 거리가 들여쓰기 깊이와 잘 대응하지만 항상 그런 것은 아닙니다 예를 들어 assert, short-circuit boolean expression, break, continue, return 같은 경우 cdg깊이가 실제 소스 코드의 들여쓰기보다 과하게 커질 수 있습니다
    
4. 논문은 각 소스 코드 문장을 그 첫 번째 바이트코드 명령어가 들어 있는 노드에 붙이고 그 노드의 들여쓰기 레벨을 적용한다고 설명합니다 그다음 첫 번째 명령어의 offset 순서대로 문장을 정렬합니다 그리고 바이트코드에는  암묵적으로 나타나지만 소스 코드에는 명시되어야 하는 else, finally, while True 같은 문장을 삽입합니다
    
    예를 들어 바이트코드에는 조건이 거짓이면 여기로 점프만 있을 수 있지만 파이썬 소스 코드로는
    
    if condition:
    ...
    else:
    ...
    
    이렇게 보여야 합니다
    
    즉 else라는 줄은 복원 과정에서 직접 넣어야 할 수 있다는 말입니다

## 실제 실험

PYLINGUAL은 디컴파일 결과를 그냥 믿지 않습니다 복원된 파이썬 소스 코드를 다시 컴파일해서 원래 PYC 바이트코드와 비교를 합니다 논문은 복원된 소스 코드를 해당 파이썬 버전의 컴파일러로 다시 컴파일한 뒤 의미에 영향을 주지 않는 차이를 줄이기 위해 도달 불가능 코드(unreachable code) 제거 같은 목표로 가는 연속 무조건 점프(unconditional jump) 병합 등을 수행한다고 설명합니다 그다음 원래 PYC와 재 컴파일 PYC의 코드 객체들이 같은 명령어 같은 인자  같은 순서를 가지는지 확인하고 exception table 같은 의미상 중요한 메타데이터도 정확히 일치하는지 검증 합니다

이 과정이 중요한 이유는 사용자가 직접 코드를 읽고 원래 코드랑 같은지 확인할 필요가 없기 때문입니다

PYLINGUAL은 NLP 모델과 기계적인 분석 구성 요소를 함께 사용합니다 논문에 따르면 PYLINGUAL 본체는 파이썬으로 작성되었고 외부 오픈소스 프로젝트 기여분을 제외하면 약 약 5.6K LOC(lines of code) 규모 입니다

| Syntax Error | Python 코드로 컴파일 자체가 안 됨 |
| No Output | 디컴파일러가 결과를 만들지 못함 |

PYLINGUAL은 기존 디컴파일러인 uncompyle6, decompyle3 보다 전반적으로 높은 perfect decompilation 비율을 보입니다 논문에서 특히 중요한 비교는

Python 3.6~3.8:
기존 디컴파일러가 비교적 잘 지원하던 구간인데도 PYLINGUAL이 더 좋음

Python 3.9~3.12:
기존 디컴파일러 지원이 약한 최신 구간에서 PYLINGUAL이 훨씬 크게 앞섬

논문은 Python 3.6~3.8에서 PYLINGUAL이 기존 최고 디컴파일러 대비 평균적으로 CSN 13.9%, PyPI 36.2%, [PyLingual.io](http://PyLingual.io) 26.0%, VirusTotal 22.4% 향상되었다고 설명합니다. Python 3.9~3.12에서는 CSN 78.0%, PyPI 74.4%, VirusTotal 48.0%, [PyLingual.io](http://PyLingual.io) 43.4% 향상되었다고 설명합니다.

특히 VirusTotal과 [PyLingual.io](http://PyLingual.io)같은 실제 악성 샘플에서는 성공률이 낮아집니다 이유는 

함수가 너무 큼
예외 처리 구조가 깊게 중첩됨
난독화가 있을 수 있음
실제 사용자 파일은 형식이 다양함

그래도 비교 대상 중에서는 PYLINGUAL 이 가장 높은 정확도를 보였습니다

EMI는 동적 테스트 기반의 동등성 판단입니다 복원된 코드를 실제로 실행해보고 입력에 대해 결과가 같은지 확인하는 방식입니다 문제가 있다면

입력 선택에 따라 결과가 달라질 수 있음
모든 입력을 테스트할 수 없음
악성코드를 실행해야 할 위험이 있음

반면 perfect decompilation 은 정적 검증입니다 코드를 실제로 실행하지 않고 다시 컴파일한 PYC를 원본 PYC 와 비교합니다 그래서 논문은 평가에 emi보다 perfect decompilation 을 사용하는 것이 더 안전하고 재현 가능하다고 봅니다

논문은 perfect decompilation 이 너무 엄격해서 실제로 의미는 같은 코드를 실패 처리할 수 있는지 확인합니다 

NumPy Python 3.8 실험에서 PYLINGUAL은 의미상 같은 결과 147개 중 2개만 perfect decompilation에서 거짓 거부되었다. uncompyle6와 decompyle3는 이 거짓 거부 비율이 더 높았습니다.

즉 perfect decompilation은 엄격하지만, PYLINGUAL에서는 지나치게 많은 정답을 버리는 수준은 아니었습니다

PyFET은 기존 디컴파일러가 죽는 입력을 전처리해서, 사람이 보기에는 비슷한 결과를 만들게 하는 방식이다.

하지만 PyFET의 목표는 **forensic equivalence**이고, 이는 수동 검증에 가까운 완화된 기준이다.

PYLINGUAL의 목표는 **perfect decompilation**, 즉 자동으로 검증 가능한 엄격한 기준이다.

논문은 PyFET이 제공한 재현 데이터셋에서도 PYLINGUAL이 더 높은 perfect decompilation 결과를 보였다고 설명합니다.

ablation study는 특정 기능을 빼면 성능이 어떻게 변하는가를 보는 실험 입니다

여기서는 먼저 Top-k segmentation search를 봅니다 5.2에서 설명한 것처럼 PYLINGUAL은 처음 분할 결과만 믿지 않고 여러 후보를 시도했습니다

처음 분할 결과
↓
확신 낮은 경계 판단을 뒤집어 추가 후보 생성
↓
여러 후보를 디컴파일
↓
perfect decompilation으로 맞는 것 검증

실험 결과 어려운 데이터셋 일수록 Top-k 검색 효과가 더 컸고 k=10 근처에서부터 성능 향상이 줄어드는  경향이 있었습니다

보정 모델의 효과도 실험 했습니다 결과적으로 보정 모델은 전체적으로 엄청 큰 차이를 만들지는 않았지만 어려운 일부 케이스에서 성능을 올렸습니다 특히 pypl데이터셋에서 효과가 더 크게 나타났습니다

논문은 일반 LLM을 그냥 디컴파일러 처럼 쓰면 어느 정도 되는지도 실험 했습니다

## 이 논문은

파이썬 바이트코드 .pyc 파일을 다시 사람이 읽을 수 있는 파이썬 소스 코드로 복원하는 디컴파일러인 PYLINGUAL을 제안하는 논문입니다

기존 도구들은 보통 파이썬 버전별로 사람이 직접 규칙을 만들어야 했습니다 하지만 파이썬 3.9 이후 특히 3.11 부터 opcode와 예외 처리 구조가 크게 바뀌면서 기존 컴파일러들이 대응하지 못했습니다 

논문이 해결하려는 문제는 

원래는 파이썬 코드는

Python 소스 코드(.py)
↓
컴파일
↓
Python 바이트코드(.pyc)
↓
Python 인터프리터가 실행

이런 식으로 실행 되는데 이걸 거꾸로 하면

Python 바이트코드(.pyc)
↓
디컴파일
↓
Python 소스 코드(.py)

이렇게 되는데 이것이 이 논문의 목표입니다

참고문헌: Wiedemeier et al., “PYLINGUAL: Toward Perfect Decompilation of Evolving High-Level Languages,” IEEE Symposium on Security and Privacy, 2025.
